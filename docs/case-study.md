# Case study: apex-design-patterns

**Problem.** Most Apex codebases contain design patterns, but few contain them on purpose: a "Singleton" someone expects to outlive the transaction, a Strategy hierarchy around an `if` that will never grow, an in-transaction listener whose failure rolls back the work it was listening to. Pattern catalogs written for Java say when to use a pattern, rarely when not to, and never what governor limits, transaction-scoped statics, the Stub API or Platform Events change.

**Approach.** A catalog of 16 patterns in a fictional Orders / Shipments / Customers domain: Builder, Factory (Custom Metadata and `Type.forName`), Singleton, Adapter, Decorator, Composite, Facade, Strategy, Template Method, Chain of Responsibility, Observer, State and Command from the Gang of Four, plus the Enterprise Integration Patterns Content-Based Router, Splitter + Aggregator and Publish-Subscribe on Platform Events. Each pattern is one self-contained folder of about 100 lines with its own tests and a card in a fixed shape: intent, the problem here, the shape in Apex, when to use it, when not to, Salesforce specifics, the production form elsewhere in the portfolio, and what the tests prove. Patterns that only make sense with real infrastructure (Idempotent Receiver, Claim Check, Dead Letter Channel, Message Store, and the PoEAA layers) are link-only rows pointing to the repos where they run at production grade, and seven GoF patterns are left out with a one-line reason each.

**Trade-offs.** The catalog ships as source, not a package: about 60 demo classes with domain names would otherwise land in a subscriber org's single global namespace, and nobody installs "the Strategy pattern". Patterns are modelled in memory first, so each card shows the pattern rather than data setup; the platform appears only where it is the point, and those tests act as a least-privilege user holding one permission set, because CI's admin holds none. Where the teaching version and the production version would diverge (persisted aggregator state, timeouts, dead-lettering), the card names the gap and links the production form instead of growing the example. Platform behaviour the code depends on was probed in a scratch org first, for example that the Automated Process user, which runs every Platform Event subscriber, may create Tasks on Orders with no permission set.

**Result.** 86 Apex tests from 17 test classes cover 100% of the repo's own classes, with a negative path and a 200-item case for each pattern, and Publish-Subscribe tested end to end with real event delivery as a Minimum Access user. Targeted mutation checks confirmed the tests fail when key behaviour is removed. CI on GitHub Actions runs Prettier, Code Analyzer (zero High, zero Moderate) and gitleaks, then deploys to a fresh scratch org per PR and reuses the PR's result on merge. Four ADRs record the distribution, layout, cross-linking and data decisions with the options rejected. The pattern selection and the "don't use it when" lists are informed by production experience at scale.

**Stack.** Apex · Platform Events · Custom Metadata · Stub API · Salesforce DX · GitHub Actions · Claude Code (`apex-standards`)
